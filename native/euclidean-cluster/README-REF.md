# euclidean-cluster：算法出处与语义说明

本模块（`src/euclidean_cluster.cc` / `.h`）是**欧式聚类（连通分量）的自研实现**，对外语义
对齐 PCL `pcl::EuclideanClusterExtraction<PointT>`（`extract_clusters.h`）的默认用法：
`setClusterTolerance` + `setMinClusterSize` + `setMaxClusterSize` + `setSearchMethod(KD-Tree)`。

## 参考出处

- 项目内保存的文章（原理与调参讲解）：`doc/点云处理欧式聚类分割/`
  （PCL 欧式聚类科普：只看欧式距离、KD-Tree 加速近邻搜索、滚雪球式生长成「朋友圈」；
  三个参数与推荐区间——`setClusterTolerance` 灵魂参数「大 → 欠分割、小 → 过分割」，
  `setMinClusterSize` 去碎噪声且**严禁设为 0**，`setMaxClusterSize` 滤异常大的背景、
  不确定时可设为总点数；并明确点出两条避坑铁律：输入须为无序点云、
  **两物体间隙小于阈值时必然被合并**）。
- PCL 文档（语义基准，未复制源码）：
  `pcl::EuclideanClusterExtraction` https://pointclouds.org/documentation/classpcl_1_1_euclidean_cluster_extraction.html
  与 `pcl::search::KdTree` https://pointclouds.org/documentation/classpcl_1_1search_1_1_kd_tree.html
- KD 树的「最长轴中点分裂 + 叶节点容量」与「按分裂元素递归左右子树」是标准做法
  （Bentley 1975 的区域查询结构；`std::nth_element` 做中位划分、查询按「轴距 > 半径则剪枝」
  是教科书通用形式），本实现独立写出。
- 并查集（Union-Find）带路径压缩 / 按秩合并：Tarjan 的经典结论；本实现用
  **根 = 分量内最小候选号** 的确定性变体（见下「为什么是并查集而不是 BFS」）。
- 对标功能：CloudCompare 的 **Label connected components**（云右键 Segment ▸ Label connected
  components…，用八叉树层级当「阈值」、按最小/最大点数过滤，产物是一组
  `CC_COMPONENT_#` 子点云放进一个组容器）。本实现与它在**产物形态**（容器 + 逐项实体）
  上一致，在**阈值语义**上不同（见差异表）。

## 为什么是 KD 树而不是「网格 + 27 邻域」

半径滤波（`native/radius-filter`）用的是规则网格：格子边长 = 半径，逐点查自身 + 26 个邻格。
那套写法在**半径 ≈ 点距**（滤波的典型输入）时非常快，但聚类的阈值是**用户调出来的物理解释
尺度**，与点距无关，且常常远大于点距。格子边长 = 阈值时：

- 稠密云里单格能塞进上万个点（阈值 0.3 m、点距 3 mm 时，一格约 100³ = 10⁶ 个点），
  查询退化成二次方——正是"测试时用稀疏云全绿、一上真实数据就卡死"的那种坑；
- 阈值小到接近点距时格子又过多（内存 O(体积/阈值³)），且绝大多数是空格。

KD 树的开销是 O(n log n) 建树 + O(n log n + 邻居对) 查询，与点距/阈值的比值无关；
文章与 PCL 也都选 KD 树。**代价**是必须先把候选平铺成连续坐标（见差异表的「点数据布局」）。

## 为什么是并查集而不是 BFS

BFS 与并查集算出的**连通分量完全相同**（连通性无关于谁先发现谁），差别在实现与并行：

- BFS 必须串行：队列是共享可变状态，「以新点为种子继续搜」是逐点推进的依赖链；
- 并查集把问题拆成「每点独立查一次半径」+「与更大的邻居 union」两步。前者只读、可任意
  分段并行；后者是并发原子操作（小根优先 CAS，**结果与执行顺序无关**）。
  `std::atomic<uint32_t>` 父指针 + 路径减半 + 段内零分配，几十万点也可轻松并行。

另一条理由是**确定性**：BFS 的簇号取决于种子发现顺序（串行下确定、并行下不确定），而并查集
只要规定「根 = 分量内最小候选号」，标签就只由输入决定 —— 这是本仓库对 native 模块的一贯要求
（同参数逐位可复现，单测才能钉住"线程无关"与"与 JS 对照逐位相等"）。

## 算法骨架（与 PCL 的对应关系）

1. **平铺候选**：按块主序收集候选点（`index` 存在则取子集），复制坐标 + 记录候选码
   `code`（= 候选序，块主序）。后续所有排序都会打乱点序，`code` 是唯一能回到"哪块哪个顶点"的钥匙。
2. **建 KD 树**：最长轴中点分裂（`std::nth_element`），叶节点 16 点；轴跨度为 0（点重合）
   时立即收作叶子，避免无限递归。
3. **半径查询 + union**：每个候选查一次 `radiusSearch`，对编号更大的邻居 `union(自身, 邻居)`。
   查询按候选区间分段并行。
4. **编号**：扫候选序 `g = 0..N-1`，`findRoot(g)` 首次遇到即分配下一个标签（1..K）并累加
   `clusterSizes[label-1]++`；第二趟把标签写回 `labels[code]`。
5. **回传**：`labels` 逐候选（**块主序**，即"第 c 块的候选点按原序"）、`clusterSizes` 长度 = K。
   渲染侧 `utils/euclideanCluster.ts#bucketClusters` 用计数排序把它摊回「每簇逐块顶点下标」
   （顶点缓冲空间），路径与 treeiso 的 `bucketCandidateLabels` 同义。

**min/max 不在这里做**（见差异表第一行）。也**不做**「簇内点数不足就地重分配」这类魔法：
过滤与否、滤掉的点去哪，都是渲染侧的明确决策。

## 已知边界（不是缺陷）

- **粘连必然合并**：两物体间隙 < 阈值时它们连通，任何实现都会把它们算成一簇（文章点名的
  死穴）。调小阈值，或用区域增长/RANSAC 之类带更多信息的算法。
- **只看距离**：不看法线、曲率、颜色——同一物体被遮挡断成两截就是两簇，不同物体贴在一起
  就是一簇。
- **单目标**：请求里虽可带多个 `entities`（契约与其余模块一致），但渲染侧每次只送一个实体。
- **内存**：native 侧峰值 ≈ 12 B/点（坐标副本）+ 4 B/点（候选码）+ 4 B/点（labels）
  - 树节点（24 B × 约 N/8 个 ≈ 3 B/点），相对输入本身（positions 12 B/点）不是量级增加；
    渲染侧预览色 3 B/点，退出预览即释放。

## 回归防线（`tests/unit/renderer/utils/euclideanCluster.spec.ts`）

- **逐位相等**：与 O(n²) 并查集 JS 对照（`utils/euclideanCluster.ts#euclideanClusterBruteForce`，
  生产禁用）在 0.1 / 0.5 / 3 三个阈值、多块 + 带 `index` 的块上 `labels` 完全相同；
- **等号边界**：`tolerance` 恰好等于点距时**合并**（`≤` 语义），`Math.fround(0.999)` 时分开；
- **线程无关**：25 万点稀疏云，`threadCount` 1 与 4 结果一致（并行路径与串行路径必须同解）；
- **跨块邻居合并**：块边界只是人为切分，接壤两点必须同簇；
- **极端阈值**：极小 ⇒ K = 候选数；极大 ⇒ K = 1；`tolerance = 0` ⇒ K = 候选数；
- **契约防御**：`index` 越界 ⇒ 该实体回空结果（不静默截断），空输入 ⇒ 空 labels。
